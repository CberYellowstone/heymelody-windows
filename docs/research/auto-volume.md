# “自动音量”的用途、机型与 Enco X4 适配边界

## 2026-10-10 处理决定：0.8.10 全机型隐藏

用户补充反馈：Enco Free4、Enco X3、Enco X4 实际均没有此功能；其他机型暂时无法确定。项目因此**统一隐藏“自动音量”／“智能音量调节”**，不按配置字段或单一能力位重新开放。Free4、X3 为使用反馈，X4 v116 另有下文的固件与实机证据；不将这一决定写成其余机型已做硬件验证。

0.8.10 从日常功能列表与 `010D` 查询中移除 `1C`，拒绝旧入口对该项的设置请求，忽略该项的 `0503` 状态及其刷新影响；同一推送中的其他功能仍正常处理。黄金听感的通知刷新与保存读回也忽略额外夹带的 `1C`，避免重复项妨碍方案同步或保存验证；其他字段与帧布局继续校验。界面从旧缓存和 Demo 中也移除此开关。独立的 `adaptiveVolume` / `30` 分支继续按原有条件工作。保留上游原始配置和协议研究，后续若有明确设备与固件证据，再单独研究是否开放。

右上信息栏改为“耳机状态提示”，保留通知订阅不完整的实际原因及“仍可手动刷新状态”的说明；读取失败按对应状态说明，不再把全部警告改写为“相关设置已禁用”。真实的其他功能异常仍会提示。

升级时需从托盘退出旧版后台，再启动包内的 0.8.10 主窗口与 Host；仅重开主窗口可能仍连接驻留的旧后台。

决定与实现全过程、原稿保全和验证日志另存本地 [0.8.10 实施档案](../../research/auto-volume-20261009/implementation-20261010/README.md)。下文保留 **2026-10-09、Host 0.8.9** 的研究基线与当时建议，不代表 0.8.10 的当前行为。

本次 0.8.10 实现通过 Windows x64 Release 的全部 13 个默认测试入口：Windows 离线检查及其余 12 个 harness 共 625 组检查。新增回归覆盖旧缓存与 Demo、通知及读取提示、`1C` 重复项隔离、独立 `30` 控制、黄金听感通知同步与保存验证。测试使用内存 transport、模拟后台及 Avalonia headless；没有对实机发送新查询或设置，也没有进行声学、原生窗口或 ARM64 执行验证。发布交由现有 GitHub Actions 构建 x64 与 ARM64。

## 2026-10-09 研究基线

2026-10-09 重新研究。官方应用中的名称是 **“智能音量调节”**：耳机根据环境噪音变化调整播放音量，调整范围受限。项目把它命名为“自动音量”，但遗漏了原厂的运行能力检查，因此 Enco X4 v116 会显示一个原厂应隐藏的禁用开关。

右上“部分状态尚未读取”的提示是另一条问题链。本轮从当前源码构建的 Host 0.8.9 实机诊断显示，原始警告是 **“部分状态通知不可用，仍可手动刷新状态。”**；Host 将所有非空警告统一替换成“部分耳机状态暂时不可用，相关设置已禁用。”。该提示在本次复现中来自部分状态通知订阅未通过，不能归因于未返回的智能音量状态。

完整对象、逐项解读、原 DEX、固件原始字节、配置快照、脚本、失败分支和实机日志保存在本地 [完整研究档案](../../research/auto-volume-20261009/README.md)，不随普通 Git clone 提供。应用源码与发布版本未因本研究修改。

## 原厂功能与显示条件

两 APK 分别独立核对了资源文案、实验室入口、设置页面、repository、SDK 请求及通知解析：无线耳机 17.6.3，以及欢律 17.6.5（原件摘要见完整档案）。它属于实验室中的环境音量适配功能，开关负责选择是否允许耳机自行调节播放音量。耳机侧的调节算法、精确幅度、触发阈值和声学效果不能由 Android 页面或配置反推出，本轮没有验证这些参数。

原厂实验室入口要求同时满足：

1. 所选型号配置 `controlAutoVolumeSupport == 1`；
2. 耳机 `0100` 能力位图解出的列表包含标记 `28`（十六进制 `1C`）。

两 APK 的映射均为 **bit 45 → 标记 28**，按 LSB 顺序解析。对于包含 status 的 `8100` payload，检查 `payload[6] & 0x20`。标记 `001C` 不是待发送的命令；`0403` 的通用设置能力也不能替代这项逐功能能力。

页面的状态来自 `010D` feature `1C`，设置经 `0403 [1C,00/01]`，后续同步经 `0503` feature 列表推送。它与项目另一个“自适应音量”分支 `adaptiveVolume` / feature `30` 是不同的配置和协议目标，不能互换。此次扫描的型号配置均未出现 `adaptiveVolume`；两应用保留相关代码也不能证明某款耳机开放了它。

## Enco X4 v116：静态与实机一致

对象为本地可信 v116 固件重建包，实机 product ID `06EC10`，双耳固件 116、盒固件 100。

| 核对项 | 结果 | 可以得出的结论 |
| --- | --- | --- |
| 两来源当前配置 | `controlAutoVolumeSupport = 1` | 型号模板声明该选项 |
| 本轮 `8100` | `payload[6] = 8F`，`8F & 20 = 0` | 当前固件未声明智能音量能力，原厂入口应隐藏 |
| `010D [01,1C]` | `810D [00,00]` | 成功响应的项目数为零，未提供该功能状态 |
| 项目使用的完整 feature 批次 | 返回 10 项，省略 `1C` 和 `1B` | 整批读取成功，未返回状态不是关闭状态 |
| 固件 GET 分发表 | `1C` 落到返回零的默认分支，上层跳过该项 | 固件静态路径解释了实际省略行为 |
| 固件 SET 分发表 | `1C` 落到默认拒绝路径 | 静态可证未实现该设置；本轮没有向实机发送 SET |

当前 Windows 的 [DailyFeatures.cs](../../src/HeyMelody.Daily/DailyFeatures.cs) 仅依型号字段添加查询和开关。读取结果没有 `1C`，于是 Value 保持未知、CanWrite 为 false。已有 [CommandCapabilities.cs](../../src/HeyMelody.Protocol/CommandCapabilities.cs) 保留了 bit 45 映射，但此控件没有利用它做原厂入口检查。

这解释了用户未在 ColorOS 或欢律中看到该功能的现象。结论限定于本次 X4 v116 及两 APK 的静态逻辑；未运行 Android 原厂页面，也不推断未来 X4 固件必然不会开放。

固件还有 `enco_adapt_vol` 等字符串，但其已核对的控制链连接的是 feature `32`（人声感知）。它们不能作为 `1C` 或 `30` 已实现的证据。

## 哪些机型声明了同一个选项

## 右上提示为何出现

本轮实际使用当前保存的欢律来源与在线缓存启动 Host worker，初始化后观察五秒。诊断与界面同时记录：

| 层级 | 实际内容 |
| --- | --- |
| `DailySnapshot.Warnings` | `部分状态通知不可用，仍可手动刷新状态。` |
| Host 映射后的 `UiSnapshot.Warnings` | `部分耳机状态暂时不可用，相关设置已禁用。` |
| 自动音量控件 | Value 未知，CanWrite 为 false |

[NativeHeadsetService.cs](../../src/HeyMelody.Host/NativeHeadsetService.cs) 的统一替换丢失了原始原因。因此本次横幅不能准确区分“通知不完整”和“某项状态不可用”。

另用生产 `DailyClient` 的内存 transport 核对六种响应：缺项、`FF`、`0`、`1`、查询拒绝及布局错误。缺项和 `FF` 会禁用该行，**自身不产生 Warnings**；拒绝和布局错误才产生相应查询警告。这与实机批次成功但缺少 `1C` 的结果一致。

## 实现影响与验证范围

后续适配宜按原厂逻辑为智能音量增加 bit 45 检查，并使用“智能音量调节”及对应用途说明；未宣告能力时隐藏，已宣告但状态读取失败时显示具体原因。警告显示应保留实际原因，使通知问题和状态读取问题各自可理解。无需针对 X4 删除型号字段或强行写入未知状态。

本轮完成两 APK 静态分析、16 份配置核对、X4 v116 固件分发表原字节分析、7 次原始 GET、当前 Host 的真实初始化与通知观察，以及 6 个内存响应场景。原始会话为 7 GET、0 SET；Host 为 18 GET、0 SET、2 次通知能力/订阅类请求。没有修改耳机设置、运行原厂 Android UI、做其他型号硬件验证或声学测试。
