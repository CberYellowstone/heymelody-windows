# 本机 ARM64 UI 卡顿调查（2026-10-23）

本轮确认的主要问题是 **Avalonia 12.1.4 的 ARM64 Adreno 默认选卡规则使普通 UI 使用 WARP 软件渲染**。独立 D3D11 探测能够正常创建 Adreno 硬件设备；相同离线窗口只改变适配器后，帧请求回调节拍和 CPU 成本均明显改善。持续更新 X4 主图还存在额外开销，见下方同源暂停对照。

这是当前电脑、当前版本的原生窗口诊断，不是所有型号、驱动或整个发布包的兼容性结论。本轮没有修改产品渲染策略、画质、驱动、电源或显示设置。

## 环境与方法

- 构建：用户提供的 0.9.2 ARM64 `257e9e6`；UI 性能改动主要来自父提交 `e2ce1a8`。未修改原始构建，GUI／Host／Filament 关键文件哈希与初次会话记录一致；这不是整包逐文件复核。
- 硬件：Snapdragon 8cx Gen 3、Adreno 690、约 16 GB RAM；Windows ARM64 build 26300，本地桌面会话，接电 Balanced。
- 显示：2560×1600、120 Hz、175%／168 DPI；诊断窗口 1280×900 DIP，原包主题和 Mica。
- 依赖：Avalonia 12.1.4、SkiaSharp／Skottie 3.119.4、.NET 10.0.13。WMI 驱动包版本为 30.0.4375.5500；ANGLE 报告所用 D3D11 组件版本为 30.0.4369.8700，两者口径不同。
- 独立 ARM64 诊断程序复用原包 MainWindow、编译 XAML、RenderingSetup 和 native DLL，用 ScenarioPreviewService 替代后台。该路径不创建真实蓝牙服务，写入方法抛异常；这是源码路径审查，不是动态 API 计数器测得“零调用”。
- 预热 10 秒、测量 20 秒；混合工作负载按真实时间驱动全程往返滚动，并每 2.5 秒展开／收起卡片。它比一般手动操作更持续，绝对数值不能直接外推日常操作。
- 每个主场景有三份不带 WPR 的样本（repeat 2／3／4）；首轮带 WPR 的样本单独用于路径和 CPU 佐证，不混入主性能表。v2 默认选卡及 v3 未暂停动画另做桥接检查。

## 主因：默认选卡主动进入 WARP

普通界面配置为 `AngleEgl → Software`，实际合成路径是 `WinUiCompositedWindowSurface`。有 Skia GPU context、加载了 GLES DLL、选择了 ANGLE，都不代表正在使用硬件 GPU。

默认路径的实际 renderer：

```text
ANGLE (Microsoft, Microsoft Basic Render Driver ... Direct3D11 ...)
```

初始化日志同时明确提示：

```text
ARM64 Adreno GPU detected; the Adreno rendering blocklist is forcing a fallback to ''microsoft basic render driver'' (typically a software renderer).
```

[Avalonia 12.1.4 对应源码](https://github.com/AvaloniaUI/Avalonia/blob/12.1.4/src/Windows/Avalonia.Win32/OpenGl/Angle/AngleWin32EglDisplay.cs#L75)在 ARM64 上启用此规则：没有应用选卡回调且存在多个适配器时，寻找第一个名称不含 Adreno 的适配器。本机 adapter 0 为 Adreno、adapter 1 为 Microsoft Basic Render Driver，因此在创建硬件设备前就主动选了 WARP；该规则未按当前驱动版本做能力检测。

独立原生 D3D11 测试中，默认硬件与显式 adapter 0 都创建成功，Adreno 支持 Feature Level 11_1。显式选卡后的 renderer 变为 `ANGLE (Qualcomm, Qualcomm(R) Adreno(TM) 8cx Gen 3 ... Direct3D11 ...)`，同时保留 ANGLE、WinUI、Mica、窗口尺寸和相同 WebP。

## 测量结果

下表是 **RequestAnimationFrame 回调节拍，不是实际显示 FPS**。Hz 和 P95 均列三份无 WPR 样本的范围；没有把不同样本的分位数拼成新的总体分位数。

| 场景 | 默认 WARP 回调 Hz | 显式 Adreno 回调 Hz |
| --- | ---: | ---: |
| X4 动态 WebP | 21.0–23.8 | 82.0–84.9 |
| X4 静态替换图 | 39.0–39.9 | 105.3–115.0 |
| 简单滚动页面 | 27.3–30.0 | 109.3–110.9 |

| 场景／适配器 | 中位数 ms | P95 ms | P99 ms |
| --- | ---: | ---: | ---: |
| X4 动态 WebP／WARP | 41.7–49.8 | 44.9–50.4 | 50.1–52.9 |
| X4 动态 WebP／Adreno | 8.7–8.7 | 17.1–23.3 | 25.0–25.2 |
| X4 静态替换图／WARP | 25.0–25.0 | 25.5–33.1 | 28.1–33.5 |
| X4 静态替换图／Adreno | 8.3–8.4 | 9.7–16.7 | 16.8–17.3 |
| 简单滚动页面／WARP | 33.3–33.6 | 33.7–42.0 | 34.5–42.6 |
| 简单滚动页面／Adreno | 8.3–8.4 | 16.4–16.5 | 17.1–17.2 |

所有主场景的 UI dispatcher P95 均低于 0.45 ms。本离线组合压力场景未出现明显 UI dispatcher 排队，低回调速率与默认 WARP 绘制路径一致；原版后台命令等待未在本轮实测。

两份单轮、带 WPR 的同类约 33 秒整段 ETL，WPA CPU 采样为：默认 WARP 157.132 CPU 秒，显式 Adreno 25.536 CPU 秒，下降约 83.75%。这包括初始化和预热，不能称为精确 20 秒稳态 CPU；不能把托管线程编号当作 ETW 系统 TID。默认路径模块统计有 89.34% 为 Unknown，现有符号／模块归属不足，未将其全部归给 WARP 函数。

## 次因：X4 动画持续更新的成本

本机欢律缓存中，X4 主图实际为 **Animated WebP**，不是 Lottie：780×780、180 帧、33 ms／帧、约 5.94 秒循环。其自身约 30.3 帧／秒的素材节奏不等于整个 UI 的帧率上限。手势说明中的 Lottie 是另一条资源路径。

为排除静态替换图的素材差异，v3 保留同一个原包 DeviceAnimatedWebpView、同源 SHA256、600×520 DIP 的 hero／view，在加载后暂停播放、等待 pending 帧稳定，再预热和测量；保留当前帧，不声称是首帧。

同一 v3 程序未暂停的桥接样本为 86.2 次回调／秒；暂停后的三份样本为 112.3–112.4 次／秒，P95 为 16.1–16.3 ms。三份测量期内都没有新的主图 draw，源 hash 和 hero／view bounds 均与未暂停场景一致；当前画面仍由合成器保留。v2 的三份未暂停主样本为 82.0–84.9 次／秒，另列于主表，不混作 v3 的同版本桥接。

该对照将额外成本定位到持续动画更新路径，尚未定量拆分 CPU 解码、像素复制、纹理上传和驱动同步各自的占比。静态审查发现：解码在 worker；正常渲染路径不等待解码锁；每帧通过 SKImage.FromPixelCopy 创建新图，780×780 RGBA 约 2.32 MiB，源节奏下约 70 MiB／秒的像素复制，之后由渲染线程替换和绘制。纹理上传／资源回收只是后续可测方向，不能当作已证实的唯一机制。

## 为什么上一轮优化收效有限

上一轮修改了脏区、缓存、动画让路和模型复制，但没有改变普通 UI 的默认选卡，因此仍在 WARP 上完成主要绘制。它们不能解除本轮确认的首要限制；本轮没有逐项回退测试，不宣称这些优化完全无效。

应用设置里的 Vulkan／OpenGL 和模型帧率只控制 Filament 三维模型，不能切换普通 Avalonia UI 后端。X4 不经过 Filament，仍重现问题，说明 3D 回读不能单独解释卡顿。WebP 也没有使用 Lottie／3D 的 AnimationYield 让帧逻辑。

## 追踪与验证边界

- 六份 CPU／GPU／DWM ETL 均为零 Lost Events／Lost Buffers。硬件路径事件量较大，WPR 自身有开销，所以首轮不作为主性能数字。
- 首份 WebP 的 PresentMon 871 行均属于 DWM；三份 baseline 的目标诊断 PID 均没有独立 Present 行，符合当前 WinUI drawing-surface 路径。本轮无法可靠给出该窗口最终上屏 FPS；没有把 DWM 刷新率、提交次数或内部 callback 冒充上屏 FPS。
- 开启原有 FPS／Render／Layout 图层的单次硬件 WebP 探测为 62.8 次回调／秒，低于关闭图层的三份主样本 82.0–84.9；图层自身会改变负载。该单次检查不用于估计通用开销比例，正式表中全部关闭图层。
- computer-use 原生通道不可用，按恢复流程重试及重置均失败。因此未执行原版窗口的人工操作回放；测试是原包 UI 的离线原生窗口副本。另用自有窗口屏幕捕获核对硬件路径的文字、卡片、X4 图像和 Mica 正常可见，未见黑窗。
- 默认 WARP 和硬件场景都属于压力测试；静态 X4 采用替换图，不能宣称与 WebP 像素完全相同。同源暂停实验用于弥补这个边界。
- 主因定位到当前 Avalonia 策略与适配器组合；没有证据据此概括“Skia 本身慢”或“本机只能低帧率”。没有验证所有窗口、弹出层、睡眠恢复、设备丢失、其它驱动、其它架构或长期运行。

## 后续修复建议（本轮未实施）

优先设计普通 UI 的后端／适配器选择策略，并记录实际 renderer、明确提示 WARP；保留兼容回退。不要把修改三维 API 设置当作普通 UI 的修复。

屏蔽规则引用了[历史 ARM64 透明窗口问题 #10405](https://github.com/AvaloniaUI/Avalonia/issues/10405)。本机主窗口的短时硬件对照通过，不足以证明所有透明窗口问题已消失；直接为所有 Adreno 全局取消屏蔽缺少验收依据。正式改变默认值前，应验证主窗口、设备管理器、校准窗口、菜单／弹出层、Mica、缩放／多屏、最小化及设备丢失恢复。

追加核查的引入提交、驱动修复社区报告、2026 年维护者取舍与回调开放过程，见 [Adreno 规则历史](avalonia-adreno-history-2026-10-23.md)。

硬件路径恢复后，再评估 WebP 持续更新的成本；以同源暂停和实际纹理／线程数据区分优化目标，保留原始素材、功能和画质。

## 证据与复现入口

后续产品策略已改为所有 Windows GUI 默认使用 DXGI 首适配器，应用设置可保存 Basic Render 兼容模式；原体验版环境变量已退役。当前设置、生效方式与失败后备见[开发说明](../development.md#界面渲染与字体)，新实现与验收另归档于 [research/ui-render-policy-20261023](../../research/ui-render-policy-20261023/README.md)。以下调查和体验版记录保留当时的行为、样本及验证范围，不作为新包的帧率实测。

调查交付后，按用户新增的本地体验要求加入 `HEYMELODY_UI_ADAPTER=adreno` 显式开关；它仅在 Windows ARM64 进程中选择 Adreno，不改变普通启动的上游默认策略、画质或 Filament 后端。体验包提供 Adreno／Avalonia 默认两个启动入口，切换前须退出旧 GUI 与托盘后台；兼容性异常时清除变量重启。上表仍是修改前的独立探针数据，不能写作新产品包的实测帧率。后续构建与定向验证另存本地档案 `local-trial-build/`，不回写原始追踪。

该 ARM64 自包含／ReadyToRun 本地构建通过包静态检查与体验 ZIP 全文件哈希核验。选卡策略定向检查 18 项通过；使用共享渲染初始化的原生窗口检查在 Adreno 和默认路径各通过 92 项，使用内存服务，未提交耳机设置。窗口位于屏外，只验证初始化、几何、主题、Mica API／实色回退和生命周期，不证明可见像素、上屏 FPS 或长期兼容性；未运行全套默认测试。

完整本地资料在 [research/ui-lag-arm64-20261023](../../research/ui-lag-arm64-20261023/README.md)，通常不随 clone 提供。包括原包哈希、环境、上游源码与问题证据、v1／v2／v3 源码和冻结二进制、运行脚本、结果 JSON／CSV、原始 ETL、采集失败与恢复记录、窗口截图，以及修改前文档副本。原始构建与设备缓存没有改写。
