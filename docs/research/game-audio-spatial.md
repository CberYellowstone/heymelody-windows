# 游戏音效与 Hi-Res／空间音效重新研究

2026-10-10 重新核对无线耳机 17.6.3（`com.oplus.melody`）、欢律 17.6.5（`com.heytap.headset`）的原 APK、原 DEX、中文资源，以及 Enco X4 v116 的原始固件字节。修复依据是：游戏音效开关使用 feature `27`，类型选择使用另一条命令；原厂资源的互斥字段不能直接变成 Windows 的禁止写入规则。

完整对象、摘要、原稿、完整源码快照、原 DEX 指令、固件反汇编、配置矩阵及失败分支保存在本地 [完整研究档案](../../research/game-audio-spatial-20261010/README.md)，不随普通 Git clone 提供。维护工具为 [game_audio_spatial_audit.py](../../tools/research/game_audio_spatial_audit.py)，只做离线读取，默认另建 `research/` 输出目录。本轮没有重新下载云配置；云证据沿用 `20261008T051557.800877Z` 的历史原件。

## 游戏开关与类型的正确命令

以下 ID 和 payload 字节均为十六进制，类型 `0/1/3` 的数值十进制与十六进制相同。

| 操作 | 读取 | 写入 | 已核对入口 |
| --- | --- | --- | --- |
| 游戏音效开关 | `010D` feature `27` | `0403 [27, value]` | 无线耳机 `ma/c.h`、欢律 `Ab/x.h` 的 feature 39（十进制）分支 |
| 游戏音效类型 | `012B []` → `[status, selectedType, count, supportedTypes…]` | `0423 [targetType, 01]` | 两包 `GameSetViewModel.h/i` 均以 `true` 调用类型 setter |

`0423` 第二字节的原参数名是 `param_game_sound_type_enable`。Android 的游戏应用前后台管理也使用这个参数；它既不是 feature `27` 的副本，也没有依据称为“禁用低延迟”。开关操作不能用类型 SET 代替，类型操作也不额外发送 feature SET。设备可能存在内部联动，最终显示以各自 GET／通知为准。

原厂类型名称是 `0 → 关闭`、`1 → 和平精英职业联赛游戏音效`、`3 → 射击类游戏音效`。X4 两来源的 `gameSoundList` 都是 `[3,0]`，固件 `012B` 同样返回两个支持类型 `[3,0]`。类型 `0` 不是“默认”。

X4 固件的 `0403` 分派经 callback `+160` 到 `100B0B10`，feature `27` 分支调用 `100AF7A0`；该路径写启用状态，不直接重写所选类型，并包含提示音 `0x25/0x26` 的调用。`012B` 经 `+1EC → 100B0FF0 → 100AF1D0`；`0423` 经 `+1F0 → 100B0FFC → 100AF960`。原始跳表、callback 表字节和初始化链均已核对，未采用旧固件中未经复核的函数别名作为证明。提示音分支还有设备状态条件，静态代码不能证明每次操作一定可听见。

Windows 保留资源与设备支持列表的交集，包括 `0`；开关和类型分别按自己的命令能力、声明及读回结果决定能否操作。当前类型为 `0`、未知值，或 feature `27` 关闭，都不应阻止用户选回支持的类型 `3`。例如 feature `27=1`、类型 `0` 时，可以同时显示“开关开／类型关闭”；不把其中一个值推导成另一个。关闭开关后也不合成类型 `0`。

## Android 界面和互斥方向

无线耳机的可见游戏音效开关使用 feature `27`；欢律在相应页面隐藏该开关，显示 feature `28` 的游戏主开关和类型选项。两包共享 setter 不等于两包显示相同的开关。无线耳机的类型 `0` 隐藏策略、关闭开关时禁用选项的策略也不能当作固件拒绝类型写入的条件。

| `gameSoundMutexes` 数值 | 地址键控 map | 原厂关联设置 |
| --- | --- | --- |
| `1` | `b` | 调音／EQ |
| `2` | `a` | 空间音效 |
| `3` | `c` | 低音增强 |
| `4` | `d` | 听感优化 |

相关对话框检查当前包名是否为 `com.heytap.headset`，而不是判断“来自无线耳机配置”。欢律在游戏音效开启时切换 EQ、低音等设置，可提示先关闭游戏音效；这是改变另一项设置时的处理方向。无线耳机正常包名为 `com.oplus.melody`，相应包名条件不成立。X4 的 `[1,3]` 不能解释为“互斥 ID 1 未知，因此禁止开启游戏音效”，也不能据此自动关闭 EQ／低音。本轮取消该错误禁止写入规则，保留原配置供研究。

两包 `GameSetFragment` 的部分 JADX 输出带有不完整标记，尤其 `hasPackages` 循环会错误呈现成始终为 false。已用原 DEX 复核：遇到非空游戏包列表会置 true；计数用的非零类型列表与实际创建 radio 的完整交集是两条路径。上述结论不依赖这个反编译错误。

## Hi-Res 与空间音效的显示状态

两包确有旧版互斥确认分支，不能概括为所有 Android 版本都没有任何限制。旧 `SpatialAudioHelper` 打开空间音效时，经确认直接调用空间 setter 的 callback，没有先写 feature `18=0`；反向打开 Hi-Res 的旧分支可先把空间模式写为 `0`。这是非对称流程，不支持项目此前的双向强制关闭另一项。

无线耳机另有 Hi-Res V2 分支：要求 `highToneQuality=2`、手机无损能力标记、系统版本条件和蓝牙设置 action，满足后直接写 Hi-Res。X4 无线耳机配置声明版本 `2`，欢律配置声明版本 `1`。空间助手还检查 Android 手机 Spatializer 是否可用；欢律明确不使用手机空间音效。手机条件不等于耳机 LE 能力，也不能直接移植到 Windows。

按本轮用户要求，Windows 的日常 Hi-Res／空间操作各自只提交用户选择的目标，不因 `spatialHiResMutex=1` 弹出关闭另一项的确认、预先关闭另一项或合成其关闭状态。该字段仍保留在资源中。耳机可能实质改变 DSP／编解码行为；界面只接受实际读回状态，不能从开启空间音效推定 Hi-Res 开关已关闭。

## 配置范围和验证边界

离线扫描两包提取配置、项目两份资源包以及历史云 run 的两来源内置／云配置，共 8 个输入、200 条相关型号记录。每个输入有 25 个相关型号，其中 17 个声明游戏类型、13 个声明 `spatialHiResMutex=1`。游戏类型除 OnePlus Buds 3 的 `[1,0]` 外均为 `[3,0]`；不能将 X4 的类型 `3` 固定成全机型唯一选项。声明了互斥字段但没有类型列表的机型，不能凭互斥字段补出类型控件。

静态审计通过：158 个输入的原件、副本与运行后 SHA256 一致，原 DEX 审计覆盖 479 个方法，所需本地来源没有缺失。修复前 Daily 116、Client 139、App 90 项模拟测试通过，但这些测试未识别错误路由和界面回滚，因此不能作为本问题已解决的证据。

修复后的默认检查通过 Daily 127、Client 154、Host 60、App 93 项；App 收据明确为模拟状态与 headless Skia 布局验证，未访问蓝牙。Windows 原生 fake 检查通过 native-smoke 59、native-backend 8 项，仍不代表真实耳机验收。默认日志、App 收据和完整产物另存 [验证保全清单](../../research/game-audio-spatial-20261010/validation/preservation-manifest.json)。

X4 v116 实机验收随后通过：使用当前 `DailyClient` 和原生 RFCOMM，游戏开关关闭／开启、类型 `0／3`、空间模式 `2`、Hi-Res 关闭／开启共 7 项操作均只提交一次目标 SET，收到匹配 ACK `0` 和目标读回。空间模式 `2` 下，Hi-Res 可回读为开启；切换 Hi-Res 也保持空间模式 `2`。这只证明开关状态，不能证明主机的音频编码或实际无损链路。

该 X4 固件选择类型 `0／3` 后，feature `27` 分别读回 `0／1`；关闭独立开关时类型仍为 `3`。这确认需要分别发布真实读回，不能把两个值强制当作相同含义。最终恢复原来的游戏开关 `1`、类型 `3`、Hi-Res `1`、空间模式 `0`，并核对其他设置未改变；worker 已退出。完整命令、原始收发字节、恢复结果及文件摘要见本地[实机收据](../../research/game-audio-spatial-20261010/live/live-acceptance.json)，原件不随普通 Git clone 提供。

首轮连接检查和一次闲置连接上的能力 GET 超时均在 SET 前终止，原始失败记录仍保留；后续读取恢复，未据此改动序号或重放未知 SET。原生窗口与回滚交互用模拟服务验证，实机采用同一 Daily 控制链的专用 harness。其他型号和固件只有静态与模拟验证。
