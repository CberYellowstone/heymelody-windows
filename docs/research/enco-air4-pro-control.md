# Enco Air4 Pro 控制连接核查

2026-10-11，针对用户反馈 OPPO Enco Air4 Pro 显示“耳机控制连接暂不可用，请双击底栏中的当前设备刷新，或三击重新连接”开展核查。源码基线为 `8b2576d` / 0.9.1；用户同时报告 Enco X4、X3、Free4 控制正常。Air4 Pro 的实际应用版本、固件与失败日志尚未提供，本轮没有连接或操作真实耳机。

完整配置投影、原 APK DEX 调用关系、第三方固定快照对照与验证记录保存在本机 [研究档案](../../research/air4-pro-control-2026-10-11/README.md)，不随普通 Git clone 提供。原资料未改写；研究阶段没有下载新云配置或改变发布版本。后续按用户授权将修复用于 0.9.2 Windows 本地构建，尚未发布到 GitHub；构建与包校验记录另保存在本机 `research/release-0.9.2-20261011/`。

## 配置与原 App 路由

核对欢律 17.6.5 与“无线耳机”17.6.3 原 APK，以及 2026-10-07 固定云配置。两来源分别保留，Air4 Pro 的产品 ID 均为 `067C10`、类型 `T1`、`supportSpp=true`，配置 UUID 均为 `0000079A-D102-11E1-9B23-00025B00A5A5`。当前内嵌配置中 X3 `067410`、X4 `06EC10`、Free4 `068C10` 也使用此 UUID。

原 APK 的连接实现从所选 `SupportDeviceConfig.getUuid()` 取得 UUID，再传入 `createRfcommSocketToServiceRecord(UUID)`；配置 UUID 非空时直接使用。未发现 Air4 Pro 专属的旧 UUID、固定 RFCOMM 通道或握手分支。OEM 中硬编码 `067C10` 的位置是诊断产品列表，不能据此改变连接协议。

Air4 Pro 的 `equalizer=2`、`multiDevicesConnect=1`、`wearDetection=1` 与部分新型号不同，应继续按功能版本、设备回报和实际 codec 决定控制。`personalNoiseCompat.minFirmVersion=150` 是个人降噪功能条件，不是建立控制连接的固件门槛。APK 配置及资源识别不能证明真机控制已经通过。

固定版本的两个 OppoPods 上游没有提供 Air4 Pro 的原始握手或 ACK 记录。其通用 UUID 备用尝试、手选通道、连接后延时及简化包处理只能提供排查线索，不能用来放宽本项目的身份、能力位图或 ACK 序号检查。版本及具体源码定位见完整档案。

## 发现与修复

原提示由 `MonitoringState.Unavailable` 触发，覆盖服务发现、RFCOMM 建连、身份/能力查询及后续读取失败。Daily 原先在重试后丢弃具体失败信息，Host 又将错误替换为固定文本，界面无法定位失败步骤。

另发现 Windows SDP 原先只读缓存，缓存没有服务记录就可能中止连接。微软说明，未指定 `LUP_FLUSHCACHE` 时，即使设备存在对应服务，查询也可能返回空结果；该标志允许实际查询远端 SDP。[Microsoft 服务发现说明](https://learn.microsoft.com/en-us/windows/win32/bluetooth/bluetooth-and-wsalookupservicebegin-for-service-discovery)

修复后的控制建连先读取所选来源允许的 UUID 的缓存；结果缺失或不唯一时，按同一 UUID 集合执行实际 SDP 查询。缓存唯一但该通道连接失败或超时时，也会实际查询一次，并以完整新结果重新选择唯一通道。初次已实际查询或最后一次建连失败时直接退出。每次打开控制会话最多两次 RFCOMM 建连，各限五秒；用户取消时停止，不继续刷新。Daily 既有两次读取尝试保持不变，worker 仍有 65 秒取消和 75 秒进程期限。最终仍须唯一服务和有效 RFCOMM 通道，普通设备列表扫描不增加远端 SDP 查询。同步 SDP 调用无法在线程内强制取消，由独立 worker 总期限隔离。

查询失败现在保留命令号，例如 `0x0103` 身份、`0x0100` 能力、`0x0106` 电量，以及超时、数据格式或 Windows 数字错误码。初次通知能力/订阅 `0x0200`、`0x0205`、`0x0201` 失败也发布具体诊断快照，并在重新读取成功后清除。服务缺失与多个服务分别显示。Host 和主界面透传这些固定诊断，并保留刷新、重连指引；不会向界面输出蓝牙地址、包内容或原始异常消息。

Supervisor 清理失败 worker 后，将详细诊断绑定到所选来源和当前连接代次，供不可用状态显示；控制状态仍按已停止连接处理。成功恢复、来源切换及设备生命周期变化会清除诊断，迟到的旧 worker 事件不能覆盖当前结果。

缓存缺项是有明确依据的连接缺陷，也是本次反馈的可能原因；缺少 Air4 Pro 失败日志和修复后复测，尚不能确定它就是该设备的实际故障原因。本轮没有改 UUID、猜测通道、跳过能力验证或自动重放设置。

### 官方固件获取与覆盖范围

欢律 17.6.5 原 APK 的固件查询为 `POST /v1/earphone/firmwareInfo`。使用产品 ID `067C10`、`softwareVersion=0`、欢律渠道和 APK 实际请求版本字段，省略 `macAddress`，官方接口返回 v125。完整保存[官方发布包](https://ocs-cn-south2.heytapcs.com/smarthome-iot-heytapmobi-com/sAjt-16128-1_all_125_0) `1_all_125_0.bin`，大小 1,148,799 字节，实得 SHA256 与官方元数据一致：`9ded6183a347beb63ba3fa10b699e833c893b8b7987f799fd8c89e270e87120f`。鉴权材料仅在内存使用，获取过程没有提供个人设备地址。

APK 的文件名解析将 `all` 解释为硬件版本通配，不能单凭名称证明镜像完整性。本样本无需基底即可独立解出代码镜像：开头为 `FFFFFFFF`，随后十五个 `BE32 压缩块长 + LZMA-alone` 块，解压合计 1,914,748 字节，SHA256 为 `168c1a32fb4dc46e2b274accb4a2c539cab8ae2ffd388aaa6b9b00bacb583fbd`。每块边界、解压结束与额外数据均已检查。尾部产品 ID 与 Air4 Pro 一致，内部 CRC 的算法和覆盖范围尚未闭合；下载大小与 SHA256 验证通过不等于内部 CRC 验证通过。

镜像包含 `best1306`、`RTX5`、`SW_VER=0.1.2.5` 和 2024-07-13 的构建标识。启动 Thumb 指令、指针与字符串地址支持执行别名 `0x0C010000` 和数据别名 `0x2C010000` 的映射分析。独立 ARMv8-M 分析轮次正确解码启动的 `MSPLIM`，恢复此前截断的启动流；主轮发现 7,139 个函数，导出全部汇编，其中 7,138 个生成 C、1 个反编译失败。自动发现与导出不等于逐函数人工理解，具体 Cortex 型号和未映射 ROM 仍有边界。完整发布包和解出的镜像是本轮静态样本，未覆盖芯片 ROM、个体 NV/校准数据，也不代表用户当前固件版本。

### 查询上下文与兼容修复

`0x0114` 是设备回报能力位 17 后执行的编码信息查询。其业务 payload 解析失败会记为 Warning；用户这条“控制数据格式无效”来自请求等待或接收帧解码层。接收 chunk 中其它帧也可能令当时的查询失败，因此提示里的命令号不能证明错误帧就是 `0x8114`。

欢律 17.6.5 与无线耳机 17.6.3 的原 DEX 已独立复核：OPOv1 接收时只取 control 的低两位，随后跳过第二头字节；固件接收 parser 也有同样规则。原实现却要求 control 整字节只能为 0–3、第二字节必须为零，会拒绝原 App 允许的帧头。本次按这两项明确规则修复接收兼容性；第二头字节的含义保持未知。v125 已核查的发送 wrapper 将这两个字段写为零，因此这项帧头修复本身不能解释该样本的查询失败。

更直接的证据来自 v125 的 `0x0114` handler：它构造 `0x8114`、原请求序号和 payload length=2，却写入 status=0 与两字节 codec，并将八字节 inner 完整传给发送 wrapper。wrapper 实发十二字节 `AA 0A 00 00 14 81 SS 02 00 00 CC 00`，其 inner 实际为八字节，按声明长度应为七字节。正常已初始化 codec 分支的 `CC` 为 1、2、8；其它 native codec 分支没有初始化这两个字节，不能将其当作新增 codec 支持。该长度矛盾会触发原严格解码器的“控制数据格式无效”。原 App 保留实际 payload，`0x8114` 业务分支读取 payload[1]，所以能继续解析正常 codec。

原始 Thumb 指令与发送链已独立校验，三份十二字节 fixture 由静态指令重构，[完整人工分析](../../research/air4-pro-control-2026-10-13/reports/firmware-control-analysis.md)记录地址、汇编、调用关系和推导过程。这些 fixture 是静态重构，不是真机抓包。

2026-10-13 的长度兼容当时仅对有证据的模式启用：现场身份/配置核验为 Air4 Pro `067C10`，本次 `0x0105` 成功查询，至少一个已报告的左右耳运行固件为 125，所有非占位的耳机运行版本均为 125。该固件会用精确字符串 `000` 表示缺失的对耳版本，当时判定忽略这个已有来源的占位值；其它未知字符串和不同运行版本阻止许可，充电盒版本不授予耳机兼容。当时还要求等待 `0x0114`，且 `0x8114` 的序号匹配、声明长度 2/实际 payload 3、status=0、codec 为 1/2/8、末字节为零。每次刷新尝试先清除许可，不从缓存、显示版本或配置门槛授予兼容。其它长度错误、FSN、分片顺序、ACK 命令与序号、单一接收通道及能力门控继续校验。此段保留旧实施与验收范围；当前策略见下节。

格式失败现在区分帧起始、帧长度、分片布局/顺序/序号、消息长度和接收不完整。仅固定原因分类通过现有异常与诊断字段传递；未知分类仍显示原泛化提示，不输出异常正文、地址或原始帧。缺失 ACK、刷新和重新连接均不重放设置。

两版 APK 的 `0x8114` 分支均固定读取 `payload[1]`，没有 count 列表或按型号/固件选择布局；内层 Packet 构造器在已由外层定界后保留实际 payload。当前把本项目的精确错长例外推广到所有已核实配置型号，不再要求 Air4 Pro 或固件 125。仍须是完整单帧、本次 pending GET `0x0114`、响应 `0x8114` 与序号匹配、声明 payload 2/实际 3、status=0、codec 为 1/2/8、末字节为零。这个 codec 白名单只限定错长补救；声明长度正确的响应仍保留未知 codec raw，不据此推断名称或控制能力。其余长度和分片错误仍拒绝。

无法识别的 `0x0114` 格式使用明确的查询失败分类，在既有最多两次读取尝试内关闭旧会话，建立新会话，重新核实身份与能力并跳过该查询；恢复会话中的后续刷新继续跳过，显式重连重新尝试。恢复不会携带旧 decoder、序号或设置事务，codec 保持未知；其它必要查询或第二次读取失败仍报告错误，缺失回执和重连不重放 SET。设备拒绝查询与格式失败分别提示，当前等待的命令号不能单独证明收到的任意坏帧属于 `0x8114`。

所有型号的固件最低条件、未满足或无法解释的固件条件默认仅作 warning，不单凭固件版本阻止连接或禁用控制；App 条件、所选配置、已实现 codec、设备回报和未知状态仍限制操作。固件提示和“编码查询不可用”沿现有 warning DTO 传到主界面右上角，长提示可悬停查看；不弹确认框，不把未验证写成不支持或真机验证通过。没有新增阻止连接的固件白名单，也没有固定旧配置：Air4 Pro 在两源内置、0928 云配置与本轮读取的 1012 云配置中条目语义均相同。
