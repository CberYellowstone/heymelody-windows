# Enco Air4 Pro 控制连接核查

2026-10-11，针对用户反馈 OPPO Enco Air4 Pro 显示“耳机控制连接暂不可用，请双击底栏中的当前设备刷新，或三击重新连接”开展核查。源码基线为 `8b2576d` / 0.9.1；用户同时报告 Enco X4、X3、Free4 控制正常。Air4 Pro 的实际应用版本、固件与失败日志尚未提供，本轮没有连接或操作真实耳机。

完整配置投影、原 APK DEX 调用关系、第三方固定快照对照与验证记录保存在本机 [研究档案](../../research/air4-pro-control-2026-10-11/README.md)，不随普通 Git clone 提供。原资料未改写；研究阶段没有下载新云配置或改变发布版本。后续按用户授权将修复用于 0.9.2 Windows 本地构建，尚未发布到 GitHub；构建与包校验记录另保存在本机 `research/release-0.9.2-20261011/`。

## 配置与原 App 路由

核对欢律 17.6.5 与“无线耳机”17.6.3 原 APK，以及 2026-10-07 固定云配置。两来源分别保留，Air4 Pro 的产品 ID 均为 `067C10`、类型 `T1`、`supportSpp=true`，配置 UUID 均为 `0000079A-D102-11E1-9B23-00025B00A5A5`。当前内嵌配置中 X3 `067410`、X4 `06EC10`、Free4 `068C10` 也使用此 UUID。

原 APK 的连接实现从所选 `SupportDeviceConfig.getUuid()` 取得 UUID，再传入 `createRfcommSocketToServiceRecord(UUID)`；配置 UUID 非空时直接使用。未发现 Air4 Pro 专属的旧 UUID、固定 RFCOMM 通道或握手分支。OEM 中硬编码 `067C10` 的位置是诊断产品列表，不能据此改变连接协议。

Air4 Pro 的 `equalizer=2`、`multiDevicesConnect=1`、`wearDetection=1` 与部分新型号不同，应继续按功能版本、设备回报和实际 codec 决定控制。`personalNoiseCompat.minFirmVersion=150` 是个人降噪功能条件，不是建立控制连接的固件门槛。APK 配置及资源识别不能证明真机控制已经通过。

固定版本的两个 OppoPods 上游没有提供 Air4 Pro 的原始握手或 ACK 记录。其通用 UUID 备用尝试、手选通道、连接后延时及简化包处理只能提供排查线索，不能用来放宽本项目的身份、能力位图或 ACK 序号检查。版本及具体源码定位见完整档案。

## 发现与修复

原提示由 `MonitoringState.Unavailable` 触发，覆盖服务发现、RFCOMM 建连、身份/能力查询及后续读取失败。Daily 原先在重试后丢弃具体失败信息，Host 又将错误替换为固定文本，界面无法定位失败步骤。

另发现 Windows SDP 原先只读缓存，缓存没有服务记录就可能中止连接。微软说明，未指定 `LUP_FLUSHCACHE` 时，即使设备存在对应服务，查询也可能返回空结果；该标志允许实际查询远端 SDP。[Microsoft 服务发现说明](https://learn.microsoft.com/en-us/windows/win32/bluetooth/bluetooth-and-wsalookupservicebegin-for-service-discovery)

修复后的控制建连先读取所选来源允许的 UUID 的缓存；结果缺失或不唯一时，按同一 UUID 集合执行实际 SDP 查询。缓存唯一但该通道连接失败或超时时，也会实际查询一次，并以完整新结果重新选择唯一通道。初次已实际查询或最后一次建连失败时直接退出。每次打开控制会话最多两次 RFCOMM 建连，各限五秒；用户取消时停止，不继续刷新。Daily 既有两次读取尝试保持不变，worker 仍有 65 秒取消和 75 秒进程期限。最终仍须唯一服务和有效 RFCOMM 通道，普通设备列表扫描不增加远端 SDP 查询。同步 SDP 调用无法在线程内强制取消，由独立 worker 总期限隔离。

查询失败现在保留命令号，例如 `0x0103` 身份、`0x0100` 能力、`0x0106` 电量，以及超时、数据格式或 Windows 数字错误码。初次通知能力/订阅 `0x0200`、`0x0205`、`0x0201` 失败也发布具体诊断快照，并在重新读取成功后清除。服务缺失与多个服务分别显示。Host 和主界面透传这些固定诊断，并保留刷新、重连指引；不会向界面输出蓝牙地址、包内容或原始异常消息。

Supervisor 清理失败 worker 后，将详细诊断绑定到所选来源和当前连接代次，供不可用状态显示；控制状态仍按已停止连接处理。成功恢复、来源切换及设备生命周期变化会清除诊断，迟到的旧 worker 事件不能覆盖当前结果。

缓存缺项是有明确依据的连接缺陷，也是本次反馈的可能原因；缺少 Air4 Pro 失败日志和修复后复测，尚不能确定它就是该设备的实际故障原因。本轮没有改 UUID、猜测通道、跳过能力验证或自动重放设置。

## 验证与下一次实测

研究阶段专项使用 .NET SDK 10.0.401：Daily 139 项、Client 163 项、Host 84 项全部通过，Windows x64 离线 SDP/ABI 检查通过；该阶段 Host 和 Avalonia App 的 Release 构建均为零警告、零错误。检查覆盖缓存命中、缓存缺失/歧义及过期通道刷新、最终歧义拒绝、身份与能力异常、必要查询/初次通知注册超时、诊断透传、来源/代次隔离和恢复清除。Air4 Pro 两来源专项采用合成回包，核对原始 profile 的三个 EQ 预设、缺失自定义 EQ 声明及未知状态门控。所有专项检查不调用蓝牙；命令、产物摘要与完整输出见本机研究档案。

后续 0.9.2 Windows 本地构建的第三次完整执行退出 0，十三个默认 runner 全部通过，共 719 项数值用例及 Windows 五组 PASS（含 App 106 项及上述 Daily、Client、Host），完成三架构共十五个 publish。完整流程零编译错误，保留一个既有 App 测试 CS0067 未使用事件警告。合并 ZIP、程序集版本、运行时、许可和九项内嵌美术的静态校验通过，收据位于 `release/HeyMelody_Windows_0.9.2_STATIC-VALIDATION.json`；十五个入口的 ReadyToRun 头与目标架构另行核对通过。这些结果只证明对应本地产物与离线范围，没有发布到 GitHub。

前两次完整构建的 Client 重连计时断言失败日志均保全。第二次定位到 400 ms 延时测得 399.946 ms，模拟服务的同设备恢复与验证快照均正常；计时断言新增 20 ms 容差，原暂停、同设备恢复和不发送 SET 的检查保留。首次失败的具体子断言原因未单独确定。构建日志位于本机 `artifacts/release-0.9.2-20261011/`，摘要、静态收据、产物 SHA256 和文档原稿位于 `research/release-0.9.2-20261011/`。
