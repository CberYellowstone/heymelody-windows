# Source and provenance

Client source is in `src`, with offline checks in `tests` and reproducible packaging in `Build-Client.ps1`. The client uses Avalonia, FluentAvalonia and CommunityToolkit.Mvvm. The Windows Bluetooth host stays separate from the cross-platform interface. The application icon was created for this client by `tools/create_app_icon.py`. Surface App screenshots and its package informed layout research; Surface artwork, fonts and package binaries are not included.

The 0.6.0 release introduced the Avalonia interface; 0.6.1 improved background state synchronization, editing and failure handling. Version 0.6.2 added a separate Avalonia/FluentAvalonia device manager, persistent device whitelist and horizontal device cards. Version 0.6.3 fixed the overlap of native and managed Close glyphs under the manager's transparent titlebar. An Avalonia Win32 window-style callback removes WS_SYSMENU to suppress native caption buttons while retaining the managed Close button and DWM Mica Alt, rounded corners and shadow. Version 0.6.4 centers each card's icon and text as a group and places the cards and trailing Add button in a shared scrolling strip. The strip is centered when it fits; overflowing selections are positioned as close to the center as the real content boundaries permit, without extra end padding. Manual scrolling is retained. Version 0.6.5 adds the supplied X4 product and earphone images and modular presentation views while retaining these earlier behaviors. Candidate selection includes paired Classic audio devices; control capabilities still require the existing model verification. Other model control protocols, macOS/Linux Bluetooth backends and the OPPO 2.3 Mbps lossless link are deferred. Source project and packaging defaults remain 0.6.0; release packaging uses an explicit version override, with `-Version 0.6.5` for this package. The interface reads its displayed version from the App assembly.

After the 0.6.4 package was generated, source changes replaced the X4 schematic and generic X4 list icon with the user-supplied `research/x4-pods-with-earphones.png` and `research/x4-both-earphones.png`. The original transparent 1440-by-1440 PNGs are copied to the App's `Assets/Devices/EncoX4` directory and embedded as Avalonia resources; the running application does not read from `research`. Their recorded provenance is the files supplied for this change, rather than the project's earlier original schematic. Other devices keep the generic drawing. The existing 0.6.4 ZIP is retained and does not contain these new assets or the associated view changes; the separate 0.6.5 package includes them.

The product-artwork and device-icon views accept display data and an `IDataTemplate` through `Visual` and `VisualTemplate`. The App resolves device appearance and supplies the templates; these hosts do not inspect Bluetooth state. Current templates display PNGs or generic drawings, with room for future font glyph, vector, Lottie or interactive 3D renderers without adding those dependencies now. Actual ProductId from a snapshot matching the selected device takes precedence over appearance inferred from a case-insensitive, trimmed exact name of OPPO Enco X4 or Enco X4. A UI-only Identity cache retains known model appearance across selection changes and disconnection, and is cleared for removed devices or a new data context. An old snapshot during selection changes is not assigned to the new selection. Name matching and cached appearance never grant control capabilities. Bitmaps are loaded lazily and shared, while each host creates its own control; application shutdown releases the image resources.

HeyMelody.DeviceManager.exe shares the GUI directory, exact runtime and dependencies; both interfaces use the separate backend worker. The manager reads cached authenticated Classic records and CoD audio hints without discovery or connection. The Host persists purpose-prefixed SHA-256 device keys to the user's separate devices.json, revalidates the complete selection before atomic replacement, and never persists ephemeral RPC identities. Windows 11 22H2 Mica Alt uses the documented DWM system backdrop interface; older systems use an opaque theme background.

Bluetooth requests remain serialized, with user submissions ahead of the next polling section. Pending submissions disable the relevant group's submission controls while selectors and EQ drafts remain editable. A user intent has at most two logical attempts: safe absolute targets can retry once after fresh verification; potentially unsafe continuation requires confirmation. Cancelling that retry confirmation or the initial spatial/Hi-Res mutex confirmation discards all pending selections, EQ drafts and unstarted writes before a full refresh. Cancelling an ordinary draft-discard or close confirmation preserves the draft. Saving EQ both saves and selects the entry; it is not a separate save-only operation. Complete backend receipts, peer acknowledgements and observed state remain distinct evidence.

Protocol fields, capability numbers and X4 model data were checked against the locally supplied HeyMelody APK and firmware evidence bundle. The embedded X4 protocol-profile JSON, separate from the display PNGs, is pinned by SHA256 in `HeyMelody.Devices/X4Profile.cs`. Details and source locations are documented in `phase5-protocol-evidence.md` and `daily-notes.md`.

The locally supplied OppoPodsManager reference (GPL-3.0-or-later) informed the research. Current parsing and workflows were implemented in the project's own protocol/control layers and independently checked against the Android source; this is not a clean-room research claim. This package does not contain the reference application's assemblies, artwork, fonts or APK.

The self-contained .NET runtimes include `LICENSE.txt` and `THIRD-PARTY-NOTICES.txt` in each architecture directory and its separate `backend` directory, copied from the exact official runtime packages used for publishing. The Avalonia interface no longer depends on the Windows Desktop runtime.

Each interface directory contains `PACKAGE-NOTICES.json` and `licenses/`. Packaging reads the resolved NuGet assets, records exact package IDs and versions, preserves NuGet license expressions/URLs and copies available license and notice files plus the package metadata. This includes native rendering dependencies such as SkiaSharp, HarfBuzzSharp and Avalonia.Native when present in the resolved dependency graph. The manifest is generated from installed packages, rather than a handwritten list that may miss an updated dependency. Build-only transitive package metadata can also appear in this notice inventory. Package restoration uses the official nuget.org feed.

Some MIT packages only include a license expression in NuGet metadata. Supplemental full upstream license texts for Avalonia, FluentAvalonia, MicroCom and Tmds.DBus, plus the Inter font's SIL Open Font License, are retained in `licenses/upstream/`. Their source revisions/URLs are recorded in `SOURCES.json`; native Skia/HarfBuzz and ANGLE notices are copied from the resolved packages.

`--ui-live-preview` can read through the real Windows host only when exactly one connected device has the exact name OPPO Enco X4. Both the service boundary and preview model reject settings. It renders one verified snapshot without polling, so it cannot validate writes, retries or simultaneous phone interaction. Providing this entry point does not establish that live hardware preview was executed for this release.

The Avalonia releases and current source do not inherit 0.5.0 hardware validation. Optional execution receipts must match the version and SHA256 of the packaged executables. The manifest and optional receipt check bind the GUI/DeviceManager/Host EXE hashes; managed application DLL hashes are recorded separately in static package reports, so EXE hashes alone do not establish correspondence with the current source. The retained 0.6.2 and 0.6.3 static receipts, `HeyMelody_Windows_0.6.2_STATIC-VALIDATION.json` and `HeyMelody_Windows_0.6.3_STATIC-VALIDATION.json` beside the release packages, verified those releases' executable and managed DLL hashes, dependencies, runtimes and notices; neither validates 0.6.4 or 0.6.5. The existing 0.6.4 package has its own `HeyMelody_Windows_0.6.4_STATIC-VALIDATION.json` report, which does not validate the subsequent X4 artwork/view changes. The 0.6.5 package has its own version-matched `HeyMelody_Windows_0.6.5_STATIC-VALIDATION.json` report. Static PE, dependency, self-contained runtime, icon and notice checks prove packaging properties; they do not prove Bluetooth behavior on a particular machine or native ARM64 execution.
