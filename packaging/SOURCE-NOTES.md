# Source and provenance

Version 0.8.6 restores GPU-first model rendering by default while preserving an explicitly saved software preference and the 0.8.5 CPU fallback. Main-window device cards no longer render or request custom device icons; product artwork and original asset provenance remain available. The hero captions are removed, ANC stays in a rounded panel, other settings start collapsed, and device information can be copied as labelled name/product/firmware text. Fully extract this version and use its matching main interface and Host after exiting the previous tray backend. These UI changes do not establish native ARM64 or Snapdragon 8cx Gen 3 hardware compatibility.

Version 0.8.5 corrects the flat, over-bright appearance of software-rendered 3D models. The pinned Ava3D software backend samples base color but omits metallic-roughness and emissive textures; applying the original white emissive factor alone made textured surfaces glow uniformly. The client derives per-mesh representative material values from UV texture samples weighted by each triangle's world surface area, uses linear metallic-roughness channels and decodes emissive sRGB before averaging, then applies a cloned fallback material and lower software lighting. Original GLB and base-color bytes remain unchanged. GPU rendering restores the original material references and lighting; Automatic mode uses the fallback when its actual backend is software. This approximation does not add per-pixel normal, occlusion or full metallic-roughness rendering. See docs/research/software-model-materials.md in the source repository for evidence and verification limits.

For 0.8.5, fully extract the package and use its matching main interface and Host after exiting the previous tray backend. GPU acceleration remains off by default. Earlier execution receipts below retain their version and hardware scope; this material correction does not establish native ARM64 or Snapdragon 8cx Gen 3 compatibility.

The verified module-14 configuration supplies `modelWebp`, an animated WebP rather than Lottie or GLB: 780 by 780 pixels, 180 frames at 33 ms each, with an infinite loop. Its original SHA256 is `269c63cccf729ea819a38cc010f6c7f6ed86fefa00bc680e84f1e4863f3d4736`. The decoder preserves the vendor bytes and handles partial-frame compositing and timing. Source-level and x64 software-rendering checks do not establish a hardware fix on Snapdragon 8cx Gen 3 or native ARM64 execution.

The product-artwork and device-icon views accept display data and an `IDataTemplate` through `Visual` and `VisualTemplate`. The App resolves device appearance and supplies the templates; these hosts do not inspect Bluetooth state. Current templates display the interactive Free4 model, the retained X4 list-icon PNG or generic drawings. Actual ProductId from a snapshot matching the selected device takes precedence over appearance inferred from a case-insensitive, trimmed exact name of OPPO Enco X4 or Enco X4. A UI-only Identity cache retains known model appearance across selection changes and disconnection, and is cleared for removed devices or a new data context. An old snapshot during selection changes is not assigned to the new selection. Name matching and cached appearance never grant control capabilities. Bitmaps are loaded lazily and shared, while each host creates its own control; application shutdown releases the image resources.

HeyMelody.DeviceManager.exe shares the GUI directory, exact runtime and dependencies; both interfaces use the shared tray backend through a bidirectional named pipe. The backend isolates native catalog enumeration and each device's RFCOMM connection in private workers. The manager reads cached authenticated Classic records and CoD audio hints without discovery or connection. The Host persists purpose-prefixed SHA-256 device keys to the user's separate devices.json, revalidates the complete selection before atomic replacement, and never persists ephemeral RPC identities. Windows 11 22H2 Mica Alt uses the documented DWM system backdrop interface; older systems use an opaque theme background.

Bluetooth commands remain serialized per device while a continuous receiver dispatches responses and notifications. Initialization, explicit refresh, settings verification and scoped notification invalidation may issue GET requests; the interface has no periodic status polling timer. Pending submissions disable the relevant group's submission controls while selectors and EQ drafts remain editable. A user intent has at most two logical attempts: safe absolute targets can retry once after fresh verification; potentially unsafe continuation requires confirmation. Cancelling that retry confirmation or the initial spatial/Hi-Res mutex confirmation discards all pending selections, EQ drafts and unstarted writes before a full refresh. Cancelling an ordinary draft-discard or close confirmation preserves the draft. Saving EQ both saves and selects the entry; it is not a separate save-only operation. Complete backend receipts, peer acknowledgements and observed state remain distinct evidence. A lost pipe receipt does not automatically replay SET.

The 0.7.0 backend uses Windows device/radio events and one BLE advertisement watcher. Notification registration, advertisement identity, battery encoding and case/placement fields were researched in the locally supplied HeyMelody APK and the OPPO phone's wireless-earphone component. The implementations and exact evidence locations are documented in `docs/research/bluetooth-events.md`; fixtures are synthetic, with no real X4 advertisement captured. BLE observations do not grant settings permissions. The existing interface layout is retained; the future case-opening popup is not included. Closing the main interface leaves the backend running, and tray exit uses the existing EQ draft confirmation. Architecture and lifecycle details are in `docs/backend-architecture.md`.

The self-contained .NET runtimes include `LICENSE.txt` and `THIRD-PARTY-NOTICES.txt` in each architecture directory and its separate `backend` directory, copied from the exact official runtime packages used for publishing. The Avalonia interface no longer depends on the Windows Desktop runtime.

Each interface directory and its separate backend directory contain `PACKAGE-NOTICES.json` and `licenses/`. Packaging reads the resolved NuGet assets, records exact package IDs and versions, preserves NuGet license expressions/URLs and copies available license and notice files plus the package metadata. This includes native rendering dependencies such as SkiaSharp, HarfBuzzSharp and Avalonia.Native when present in the resolved dependency graph. The manifest is generated from installed packages, rather than a handwritten list that may miss an updated dependency. Build-only transitive package metadata can also appear in this notice inventory. Package restoration uses the official nuget.org feed.

Some MIT packages only include a license expression in NuGet metadata. Supplemental full upstream license texts for Avalonia, FluentAvalonia, MicroCom and Tmds.DBus, plus the Inter font's SIL Open Font License, are retained in `licenses/upstream/`. Their source revisions/URLs are recorded in `SOURCES.json`; native Skia/HarfBuzz and ANGLE notices are copied from the resolved packages.
